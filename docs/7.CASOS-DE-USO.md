# 7. Casos de uso

Tres herramientas actuales que implementan MCP, qué rol cumplen en la arquitectura del
punto 4 y para qué lo usan.

## 7.1 Claude Code y Claude Desktop (Anthropic)

**Rol: host.** Son las aplicaciones donde nació el protocolo (Anthropic publicó MCP como
estándar abierto en noviembre de 2024) y siguen siendo la implementación de referencia del
lado del host.

Para qué usan MCP:

- **Servidores locales por stdio**: sistema de archivos, git, navegador, bases de datos.
  Es el caso que instalamos en esta práctica.
- **Conectores remotos por Streamable HTTP**: servicios como GitHub, Notion, Figma o
  Sentry, autenticados con OAuth desde la propia aplicación.
- **Distribución empaquetada**: servidores MCP y *skills* que se instalan como plugins con
  un comando, en lugar de editar JSON a mano.

En el caso de Claude Code (CLI/IDE), el uso típico es trabajar sobre un repositorio
completo: el agente lista el árbol, lee los archivos relevantes, propone ediciones, corre
pruebas en la terminal y repite, todo desde la máquina local.

## 7.2 Google Antigravity (entorno de desarrollo agéntico)

**Rol: host.** Antigravity es el entorno de desarrollo agéntico de Google —con un IDE
derivado de VS Code, una app de escritorio y una CLI (`agy`) que reemplazó a Gemini CLI—
construido alrededor de agentes que trabajan sobre el código en lugar de solo sugerirlo.

Para qué usa MCP:

- Tiene un **MCP Store** integrado en el panel de agente (**Additional options → MCP Servers
  → Manage MCP Servers**) y un manifiesto JSON editable (`mcp_config.json`, bajo
  `~/.gemini/antigravity/`), donde se registran tanto servidores locales como remotos por
  URL.
- Se pueden mencionar servidores MCP como contexto con `@` dentro de la conversación con el
  agente.
- Google publica servidores MCP para su *Data Cloud* mediante **MCP Toolbox for Databases**,
  de modo que el agente consulte esquemas y ejecute SQL contra BigQuery, AlloyDB, Cloud SQL,
  Spanner o Looker sin salir del IDE.
- Flujos concretos documentados por terceros: instalar el servidor MCP de Dart/Flutter para
  desarrollo móvil, o servidores de datos externos (p. ej. CoinGecko) para consultar APIs
  en vivo desde el agente.


## 7.3 VS Code + GitHub Copilot (modo agente)

**Rol: host.** MCP llegó a VS Code Stable en la versión **1.102 (julio de 2025)**, junto con
la disponibilidad general del modo agente.

Para qué lo usa:

- Los servidores se declaran en `.vscode/mcp.json` (alcance del workspace, versionable en el
  repositorio) o en la configuración de usuario. Detalle práctico: la clave raíz aquí es
  `servers`, no `mcpServers` como en Claude Desktop o Cursor.
- **Las herramientas MCP solo se ejecutan en modo agente** (*Agent*), no en modo *Ask*. Es
  la causa más común de "configuré el servidor y no hace nada".
- GitHub publica su propio **servidor MCP remoto** (`https://api.githubcopilot.com/mcp/`)
  para repositorios, issues, PRs y búsqueda de código, además de una versión local.
- Para organizaciones, existen controles de gobierno: la política "MCP servers in Copilot"
  viene deshabilitada por defecto en Copilot Business/Enterprise, y se puede restringir qué
  servidores del registro están permitidos.

### Otras implementaciones relevantes

- **Cursor**: IDE agéntico con configuración por `mcp.json` y un catálogo maduro de
  servidores.
- **ChatGPT / OpenAI**: soporte de MCP a través del Apps SDK y de las herramientas de
  agentes de su plataforma.
- **Visual Studio 2022/2026 y JetBrains**: soporte de MCP en sus asistentes.
- **Registros**: existe un **registro oficial de MCP** (índice central de servidores con
  verificación de propiedad por DNS y OAuth de GitHub) y el registro de GitHub
  (`github.com/mcp`), que alimenta la galería `@mcp` de VS Code y las listas permitidas de
  empresa.

## 7.4 Cómo editan repositorios completos sin subir archivos manualmente

Esta es la parte que más se malinterpreta. El repositorio **nunca se sube** al proveedor del
modelo. Lo que ocurre es esto:

1. **El servidor MCP corre en tu máquina.** El host lo lanza como proceso hijo por stdio, y
   le pasa como directorio permitido (o como *root*) la carpeta del workspace abierto. El
   servidor tiene acceso al disco; el modelo no.
2. **El agente descubre el catálogo** con `tools/list`: listar, leer, buscar, escribir,
   editar. Esas descripciones entran en su contexto.
3. **Bucle agéntico**, un paso a la vez:
   - `directory_tree` o `search_files` para ubicarse (no lee todo el repo: busca).
   - `read_text_file` sobre los pocos archivos relevantes.
   - `edit_file` con pares `oldText` / `newText`, que devuelve un **diff** en lugar de
     reescribir el archivo entero.
   - Ejecutar pruebas o el compilador (con un servidor de terminal o la integración del
     IDE), leer el error y volver a editar.
4. **Solo viaja texto, y solo el necesario.** Hacia el proveedor del modelo suben los
   fragmentos que el agente decidió leer y los diffs que decidió escribir — no el árbol
   completo ni los binarios. Por eso funciona en repos que no cabrían en ninguna ventana de
   contexto: la selección la hace el propio agente, iterando.
5. **La revisión queda del lado humano**: diffs en el editor, confirmación por llamada
   destructiva, y `git diff` / `git checkout` como red de seguridad.

Para servicios remotos el esquema es análogo pero el disco no participa: el servidor MCP de
GitHub, por ejemplo, corre como servicio y traduce las llamadas del modelo a la API REST de
GitHub, de modo que el agente puede abrir un PR sin que ningún archivo haya pasado por tu
máquina.

**La idea de fondo:** el repositorio no se "sube" porque el modelo no necesita tenerlo — le
basta con poder **pedir** pedazos de él a un programa que sí lo tiene. Eso es, exactamente,
lo que resuelve MCP.

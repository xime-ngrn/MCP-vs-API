# 3. MCP frente a una API *(punto obligatorio)*

> Resumen en una línea: **una API es un contrato que un programador cablea en tiempo de
> desarrollo; MCP es un protocolo que publica un catálogo para que el modelo elija en tiempo
> de ejecución. No compiten: casi todo servidor MCP es una envoltura sobre una API.**

## 3.1 Qué es una API

Una **API** (*Application Programming Interface*) es un contrato entre programas: define
qué operaciones expone un servicio, qué parámetros acepta cada una, qué devuelve y qué
errores puede producir. El caso típico en la web es una API REST o GraphQL sobre HTTP.

El flujo de trabajo de una integración con API es **humano y previo a la ejecución**:

1. La persona desarrolladora lee la documentación.
2. **Decide** qué endpoint corresponde al caso de uso.
3. Arma la petición: método, URL, encabezados, autenticación, cuerpo.
4. Escribe el código que interpreta la respuesta y maneja los errores.
5. Compila / despliega. A partir de ahí, la decisión ya está congelada en el código.

```python
# Integración clásica con API: la decisión está escrita de antemano.
import requests

def clima_actual(ciudad: str) -> str:
    r = requests.get(
        "https://api.ejemplo.com/v1/weather",      # yo elegí este endpoint
        params={"q": ciudad, "units": "metric"},   # yo elegí estos parámetros
        headers={"Authorization": f"Bearer {API_KEY}"},
        timeout=10,
    )
    r.raise_for_status()
    datos = r.json()
    return f"{datos['temp']} °C, {datos['description']}"  # yo elegí qué campos leer
```

El programa **no descubre** nada: si mañana el servicio agrega `/v1/air_quality`, este
código no se entera. Para aprovecharlo hay que leer docs otra vez, escribir código otra vez
y volver a desplegar. Este es el llamado **problema N×M**: `N` aplicaciones que quieren
hablar con `M` servicios requieren `N×M` integraciones escritas a mano.

## 3.2 Qué es MCP

**MCP (Model Context Protocol)** es un **protocolo abierto**, publicado originalmente por
Anthropic en noviembre de 2024 y hoy mantenido como estándar abierto, basado en
**JSON-RPC 2.0**. Define cómo una aplicación de IA se conecta a fuentes de contexto y
herramientas externas.

La pieza central: un **servidor MCP publica un catálogo de herramientas**, y cada entrada
del catálogo lleva:

- `name`: identificador de la herramienta,
- `description`: descripción en lenguaje natural, escrita *para que la lea el modelo*,
- `inputSchema`: esquema JSON Schema de sus parámetros (y opcionalmente `outputSchema`),
- anotaciones opcionales (`readOnlyHint`, `destructiveHint`, `idempotentHint`,
  `openWorldHint`) que le dicen al cliente qué tan peligrosa es la operación.

El cliente pide ese catálogo con `tools/list` **en tiempo de ejecución**, lo inyecta en el
contexto del modelo, y **el modelo decide** cuál invocar según lo que pidió el usuario. La
invocación viaja como `tools/call`.

```jsonc
// 1) El cliente descubre el catálogo en tiempo de ejecución
→ {"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}

← {"jsonrpc":"2.0","id":1,"result":{
     "resultType":"complete",
     "tools":[
       {"name":"read_text_file",
        "description":"Read complete contents of a file as text.",
        "inputSchema":{"type":"object",
                       "properties":{"path":{"type":"string"},
                                     "head":{"type":"number"}},
                       "required":["path"]},
        "annotations":{"readOnlyHint":true,"openWorldHint":false}},
       {"name":"write_file", "...":"..."}
     ]}}

// 2) El modelo eligió la herramienta y sus argumentos; el host ejecuta la llamada
→ {"jsonrpc":"2.0","id":2,"method":"tools/call",
   "params":{"name":"read_text_file","arguments":{"path":"/proyecto/README.md"}}}

← {"jsonrpc":"2.0","id":2,"result":{
     "resultType":"complete",
     "content":[{"type":"text","text":"# Proyecto ...\n"}],
     "isError":false}}
```

Nadie escribió en el código "si el usuario pregunta por el README, llama a
`read_text_file`". Esa decisión la tomó el modelo leyendo las descripciones del catálogo.
Eso es lo que cambia el eje de la comparación: **el momento y el sujeto de la decisión.**

> Nota de versión: en la revisión `2026-07-28` todo resultado lleva un campo obligatorio
> `resultType` (`"complete"` o `"input_required"`), y cada petición transporta su versión de
> protocolo y capacidades en `_meta`, porque el protocolo dejó de tener sesión.

## 3.3 Tabla comparativa

| Eje | **API tradicional (REST/GraphQL)** | **MCP** |
|---|---|---|
| **Quién decide qué se invoca** | La persona desarrolladora, **antes** de ejecutar: la elección de endpoint y parámetros está escrita en el código fuente | El **modelo**, en tiempo de ejecución, a partir del catálogo y de la petición del usuario. El host aplica la política y ejecuta |
| **Cuándo se toma la decisión** | En tiempo de desarrollo (*design time*) | En tiempo de ejecución (*runtime*), en cada turno de la conversación |
| **Cómo se descubren las capacidades** | Documentación para humanos (OpenAPI/Swagger, portal de developers). El programa no descubre nada por sí mismo | Descubrimiento programático: `tools/list`, `resources/list`, `prompts/list`, y `server/discover` para versiones y capacidades. El catálogo llega con descripciones legibles por el modelo y esquemas de parámetros |
| **Acoplamiento cliente–servicio** | **Fuerte.** El cliente conoce rutas, verbos, nombres de campos y versiones. Un cambio en el servicio rompe el cliente | **Débil.** El cliente solo sabe hablar MCP; no conoce el dominio del servidor. Si el servidor agrega o cambia herramientas, el mismo cliente las ve en el siguiente `tools/list` sin recompilar |
| **Formato de los mensajes** | Libre por servicio: JSON, XML, protobuf, *form-encoded*; semántica de verbos y códigos HTTP definida por cada API | **Uniforme:** JSON-RPC 2.0 (`method`, `params`, `id`, `result`/`error`) para todos los servidores. Contenidos tipados (`text`, `image`, `audio`, `resource`) y esquemas JSON Schema 2020-12 |
| **Autenticación** | Definida por cada servicio: API key en encabezado, OAuth 2.0, JWT, HMAC, mTLS… La credencial vive en el código o en variables de entorno del cliente | Normalizada por transporte: **stdio** hereda las credenciales del proceso (variables de entorno, archivos de config local); **Streamable HTTP** usa el perfil de autorización del protocolo, basado en OAuth 2.1, con metadatos de recurso protegido, validación del emisor (`iss`, RFC 9207) y —desde `2026-07-28`— *Client ID Metadata Documents* en lugar de registro dinámico de cliente |
| **Consentimiento** | No existe como concepto del contrato: el código ya fue autorizado por quien lo escribió | Es **parte explícita del diseño**: el host muestra la llamada propuesta y sus argumentos, y la persona aprueba o rechaza. Las anotaciones de herramienta (`readOnlyHint`, `destructiveHint`) existen para que el cliente decida qué exige confirmación |
| **Reutilización entre aplicaciones** | Nula: cada aplicación reescribe su integración. Problema **N×M** | Alta: un servidor MCP escrito una vez funciona con **cualquier** host compatible (IDE agéntico, app de escritorio, CLI, agente propio). Problema **N+M** |
| **Manejo de errores** | Códigos HTTP + cuerpos de error específicos de cada API, interpretados por código escrito a mano | Errores JSON-RPC estandarizados, más errores de herramienta (`isError: true` con texto) pensados para que **el modelo** los lea y reintente o cambie de estrategia |
| **Quién lee la documentación** | Una persona | El modelo (las `description` del catálogo *son* la documentación) |
| **Costo de agregar una capacidad** | Nuevo código en cada cliente + despliegue | Agregar una herramienta en el servidor; los clientes la ven al siguiente listado |
| **Determinismo** | Alto: la misma entrada produce la misma llamada | Menor: el modelo puede elegir otra herramienta, otros argumentos u otro orden. Esto es la ventaja (flexibilidad) y el riesgo (imprevisibilidad) |

## 3.4 MCP **no** sustituye a las APIs

Este punto conviene dejarlo escrito sin ambigüedad, porque es donde más se confunde el
tema:

1. **Un servidor MCP casi siempre envuelve algo que ya existía.** El servidor MCP de
   GitHub llama a la API REST de GitHub. Un servidor MCP de base de datos abre una conexión
   y ejecuta SQL. El servidor de sistema de archivos llama a las funciones `fs` de Node.js,
   que a su vez son llamadas al sistema operativo. Si la API desaparece, el servidor MCP
   deja de funcionar.
2. **MCP es una capa por encima, no un reemplazo.** Su aporte es hacer que un recurso
   preexistente sea **descubrible y utilizable por un modelo**: le pone nombres, esquemas y
   descripciones en lenguaje natural, y unifica el transporte, la autorización y el
   consentimiento.
3. **El trabajo de integración no desaparece: se reubica.** Alguien tiene que escribir el
   servidor MCP, y ese alguien lee la documentación de la API exactamente como antes. La
   diferencia es que ese trabajo se hace **una vez por servicio** y lo reutilizan todos los
   hosts, en lugar de una vez por cada par (aplicación, servicio).
4. **Hay casos donde MCP es la herramienta equivocada.** Si el flujo es determinista, de
   alto volumen, sensible a la latencia o al costo —cobrar una tarjeta, procesar un lote
   nocturno, responder un endpoint de producción—, se llama a la API directamente. MCP
   aporta cuando la tarea es abierta, exploratoria y la decide una persona en lenguaje
   natural.

| Situación | Conviene |
|---|---|
| Flujo fijo, alto volumen, latencia crítica, resultado auditable paso a paso | **API directa** |
| Tarea abierta descrita en lenguaje natural, catálogo amplio, orden de pasos desconocido de antemano | **MCP** |
| Un mismo recurso consumido por varios asistentes/IDEs distintos | **MCP** (encima de la API) |
| Integración única entre dos servicios sin un modelo de por medio | **API directa** (MCP no aporta nada ahí) |

### Analogía útil (con su límite)

MCP se describe a menudo como "el USB-C de las aplicaciones de IA": un conector estándar
que reemplaza un cable distinto por cada dispositivo. La analogía sirve para la
estandarización del puerto, pero se queda corta en lo esencial: en USB-C el usuario decide
qué enchufa; en MCP, una vez enchufado, **quien elige qué se usa y cuándo es el modelo**.

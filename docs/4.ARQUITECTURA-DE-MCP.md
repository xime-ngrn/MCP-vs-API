# 4. Arquitectura de MCP

> **Versión de la especificación consultada: `2026-07-28`. Fecha de consulta: 20 de
> septiembre de 2026.** Las revisiones de MCP se nombran por fecha. Hasta hoy existen cinco:
> `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25` y `2026-07-28`. La sección 4.6
> detalla qué cambió, porque esta última revisión rompe compatibilidad con lo que describe
> la mayoría del material disponible en línea.

## 4.1 Modelo host / cliente / servidor

MCP sigue una arquitectura **cliente-host-servidor**, donde un host puede ejecutar varias
instancias de cliente a la vez.

| Rol | Qué hace | Quién lo cumple en nuestro ejemplo |
|---|---|---|
| **Host** | Es la aplicación de IA. Contiene al modelo (o habla con él), crea y administra los clientes, decide a qué servidores conectarse, **aplica las políticas de seguridad y pide consentimiento al usuario**, y agrega el contexto de todos los servidores para armar el prompt | La aplicación de escritorio / IDE con soporte MCP (Claude Desktop, Claude Code, VS Code con Copilot en modo agente, Antigravity, Cursor…) |
| **Cliente** | Componente creado por el host que mantiene la relación **1:1 con un servidor**. Adjunta a cada petición la versión de protocolo y las capacidades, enruta mensajes JSON-RPC y mantiene la frontera de aislamiento entre servidores | La instancia de cliente MCP que el host crea para el servidor `filesystem`. Si además conectamos un servidor `git`, el host crea un **segundo** cliente independiente |
| **Servidor** | Expone capacidades concretas y acotadas a través de las primitivas del protocolo. Puede ser un proceso local o un servicio remoto. No conoce al modelo ni al usuario: solo responde peticiones JSON-RPC | `@modelcontextprotocol/server-filesystem`, lanzado por el host como proceso hijo con `npx -y @modelcontextprotocol/server-filesystem /ruta/permitida` |

```text
┌──────────────────────── HOST (aplicación de IA) ───────────────────────┐
│                                                                        │
│   modelo  ◀──── contexto agregado ────┐                                │
│     │                                 │                                │
│     └── "quiero llamar a read_text_file(path=...)"                     │
│                                       │                                │
│   política + consentimiento del usuario                                │
│                                       │                                │
│   ┌── Cliente A ──┐   ┌── Cliente B ──┐   ┌── Cliente C ──┐            │
└───┼───────────────┼───┼───────────────┼───┼───────────────┼────────────┘
    │ JSON-RPC 2.0  │   │               │   │                │
    ▼ (stdio)       ▼   ▼ (stdio)       ▼   ▼ (HTTP)         ▼
 Servidor filesystem   Servidor git      Servidor remoto (API de terceros)
     └─▶ fs de Node      └─▶ binario git     └─▶ API REST del servicio
```

Obsérvese el punto del punto 2: el modelo sigue sin tocar el disco. Lo tocan los servidores,
en nombre del host, con autorización del usuario.

## 4.2 Primitivas del lado del servidor

Un servidor puede exponer tres tipos de primitivas. La distinción importante entre ellas es
**quién controla su uso**:

| Primitiva | Control | Para qué sirve | Métodos JSON-RPC |
|---|---|---|---|
| **Herramientas** (*tools*) | **El modelo** (*model-controlled*): el modelo decide invocarlas a partir del contexto | Funciones ejecutables con efectos: leer/escribir archivos, consultar una base, llamar una API, enviar un mensaje | `tools/list`, `tools/call` |
| **Recursos** (*resources*) | **La aplicación** (*application-driven*): el host decide qué cargar en el contexto | Datos identificados por URI que aportan contexto: contenido de archivos, filas de una tabla, respuestas de una API, esquemas | `resources/list`, `resources/read`, `resources/templates/list` |
| **Plantillas de prompt** (*prompts*) | **El usuario** (*user-controlled*): la persona la selecciona explícitamente | Flujos preparados y parametrizables ("revisa este código", "resume este PR") que el servidor ofrece como comandos o *slash commands* | `prompts/list`, `prompts/get` |

Las tres se **descubren en tiempo de ejecución** con sus respectivos `*/list`. Desde
`2026-07-28`, los resultados de esos listados incluyen `ttlMs` y `cacheScope`, para que el
cliente pueda cachearlos en vez de consultarlos en cada turno.

## 4.3 Primitivas del lado del cliente

Son capacidades que **el cliente** ofrece al servidor. Históricamente fueron tres:

| Primitiva | Qué hace | Estado en `2026-07-28` |
|---|---|---|
| **Roots** | El cliente le comunica al servidor los directorios o URIs sobre los que tiene permitido operar (típicamente, la carpeta del *workspace* abierto) | **Deprecada.** Sigue funcionando durante la ventana de deprecación (mínimo 12 meses), pero la migración sugerida es pasar rutas como parámetros de herramienta, como URIs de recurso o por configuración del servidor |
| **Sampling** | El servidor le pide al cliente que ejecute una inferencia del modelo, sin tener que contratar su propio proveedor de LLM | **Deprecada.** Migración sugerida: integrarse directamente con la API del proveedor |
| **Elicitation** | El servidor solicita información adicional al usuario a mitad de una operación (confirmar algo, pedir un dato faltante) | **Vigente**, pero reformulada bajo el patrón MRTR (ver abajo) |

**MRTR (*Multi Round-Trip Requests*)** es el patrón que en `2026-07-28` reemplazó a las
peticiones iniciadas por el servidor (`roots/list`, `sampling/createMessage`,
`elicitation/create`). Como el protocolo ya no tiene sesión ni canal bidireccional
permanente, el servidor no puede "llamar de vuelta" al cliente. En su lugar:

1. El servidor responde con un resultado interino `resultType: "input_required"` cuyo campo
   `inputRequests` contiene lo que necesita.
2. El cliente obtiene esa información (preguntándole al usuario, por ejemplo).
3. El cliente **reintenta la petición original** agregando `inputResponses`.

## 4.4 Los dos transportes

| Transporte | Cuándo se usa | Cómo funciona |
|---|---|---|
| **stdio** | Servidores **locales**, que corren en la misma máquina que el host | El host lanza el servidor como **proceso hijo** y habla con él por `stdin`/`stdout`, un mensaje JSON-RPC por línea. `stderr` queda para logs. No hay red, no hay puerto abierto, no hay OAuth: la autorización es la del propio usuario del sistema operativo. Es el transporte del servidor de sistema de archivos |
| **Streamable HTTP** | Servidores **remotos**, expuestos como servicio | Un único endpoint HTTP que recibe `POST` con el mensaje JSON-RPC en el cuerpo. La respuesta puede ser JSON simple o un flujo SSE cuando hay resultados parciales. Requiere autorización (perfil basado en OAuth 2.1) y validación de `Origin` contra *DNS rebinding* |

Detalles de `2026-07-28` para Streamable HTTP:

- Cada `POST` debe llevar los encabezados `MCP-Protocol-Version`, **`Mcp-Method`** y
  **`Mcp-Name`**, para permitir enrutamiento y políticas sin abrir el cuerpo del mensaje.
- Desapareció el encabezado `Mcp-Session-Id` y el endpoint `GET`. Las notificaciones del
  servidor al cliente ahora van por un flujo `subscriptions/listen` al que el cliente se
  suscribe explícitamente.
- El transporte antiguo **HTTP+SSE** (dos endpoints), obsoleto desde `2025-03-26`, quedó
  formalmente clasificado como *Deprecated*.

```http
POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: read_text_file
Content-Type: application/json

{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"read_text_file","arguments":{"path":"/proyecto/README.md"},
           "_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28",
                    "io.modelcontextprotocol/clientInfo":{"name":"mi-host","version":"1.0"}}}}
```

## 4.5 Descubrimiento y capacidades

MCP negocia capacidades: cada parte declara qué soporta y ambas deben respetarlo.

- El cliente envía sus capacidades **en cada petición**, dentro de
  `_meta.io.modelcontextprotocol/clientCapabilities`, junto con
  `io.modelcontextprotocol/protocolVersion` y `io.modelcontextprotocol/clientInfo`.
- El servidor **debe** implementar `server/discover`, el método por el que anuncia las
  versiones de protocolo que soporta, sus capacidades y su identidad. El cliente puede
  llamarlo antes que cualquier otra cosa para elegir versión por adelantado, o usarlo como
  sonda de compatibilidad sobre stdio.
- Las capacidades se pueden extender mediante el nuevo campo `extensions` de
  `ClientCapabilities` / `ServerCapabilities` (marco formal de extensiones, donde ahora vive
  por ejemplo `io.modelcontextprotocol/tasks`).

## 4.6 Qué cambió en `2026-07-28` (y por qué hay que decir la versión)

La mayoría de los tutoriales, cursos y diagramas que circulan describen el modelo
`2025-06-18`: sesión con *handshake* `initialize`, `Mcp-Session-Id`, peticiones iniciadas
por el servidor, Roots y Sampling como primitivas vigentes. Eso ya no es la especificación
actual. Cambios principales de la revisión `2026-07-28`:

1. **MCP es ahora un protocolo sin estado.** Se eliminó el intercambio
   `initialize` / `notifications/initialized`; cada petición es autosuficiente y transporta
   su versión y capacidades en `_meta`.
2. **Se eliminaron las sesiones de protocolo** y el encabezado `Mcp-Session-Id` del
   transporte Streamable HTTP. Los listados (`tools/list`, `resources/list`,
   `prompts/list`) ya no varían por conexión. El estado que un servidor necesite conservar
   se maneja con identificadores explícitos que viajan como argumentos normales de
   herramienta.
3. **Nuevo método obligatorio `server/discover`.**
4. **`subscriptions/listen`** reemplaza al endpoint GET y a
   `resources/subscribe`/`unsubscribe`.
5. **Se eliminaron `ping`, `logging/setLevel` y `notifications/roots/list_changed`.**
6. **Tasks** salió del núcleo a la extensión oficial `io.modelcontextprotocol/tasks`, con
   `tasks/get` por *polling* y `tasks/update`.
7. **MRTR** reemplaza a las peticiones iniciadas por el servidor.
8. **`resultType` obligatorio** en todos los resultados.
9. **Endurecimiento de autorización**: validación del `iss` (RFC 9207) y desplazamiento del
   registro dinámico de clientes (DCR) hacia *Client ID Metadata Documents* (CIMD).
10. **Deprecaciones formales**: Roots, Sampling y Logging, con política de ciclo de vida y
    ventana mínima de 12 meses antes de la eliminación.

**Implicación práctica para la práctica:** el servidor de referencia de sistema de archivos
que instalamos todavía está escrito contra el modelo anterior (usa `initialize` y Roots).
Eso es normal y está previsto: los SDK y los servidores adoptan cada revisión a su propio
ritmo, y el mecanismo de negociación de versión existe justamente para que convivan.

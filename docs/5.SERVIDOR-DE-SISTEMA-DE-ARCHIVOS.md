# 5. El servidor de sistema de archivos

## 5.1 "FS" no es parte del protocolo

Conviene empezar deshaciendo una confusión común: **no existe un "MCP-FS" ni un módulo de
archivos dentro de la especificación**. La especificación define transporte, mensajes
JSON-RPC y primitivas (tools, resources, prompts); no dice nada sobre archivos.

Lo que instalamos es **uno de los servidores de referencia** del repositorio
[`modelcontextprotocol/servers`](https://github.com/modelcontextprotocol/servers),
publicado en npm como `@modelcontextprotocol/server-filesystem`. Es un servidor **entre
muchos otros posibles**: en el mismo repositorio conviven servidores de referencia para
`git`, `fetch`, `memory`, `sequentialthinking`, `time` y `everything`, y fuera de él existen
cientos de servidores de terceros (GitHub, Slack, Postgres, Figma, Notion, navegadores,
bases vectoriales…). Si mañana nadie usara el servidor de archivos, MCP seguiría siendo
exactamente el mismo protocolo.

Su valor didáctico es otro: es el caso mínimo donde se ve con claridad el problema del
punto 2 (un modelo no puede tocar el disco) y su solución (un proceso local que sí puede,
hablando MCP).

## 5.2 Instalación y configuración típica

```jsonc
// Configuración del host (ejemplo, transporte stdio)
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "/Users/usuario/Desktop",
        "/ruta/a/otro/directorio/permitido"
      ]
    }
  }
}
```

El host lanza ese comando como proceso hijo y se comunica por stdin/stdout. En Windows hay
que envolverlo con `cmd /c`. También existe imagen de Docker (`mcp/filesystem`), donde los
directorios se montan bajo `/projects`, y se puede agregar la bandera `ro` al montaje para
dejarlos **de solo lectura**.

## 5.3 Herramientas que expone

El servidor publica 13 herramientas, agrupadas por lo que hacen:

| Herramienta | Operación | Entradas principales |
|---|---|---|
| `list_directory` | Listar un directorio, con prefijos `[FILE]` / `[DIR]` | `path` |
| `list_directory_with_sizes` | Igual, con tamaños y totales | `path`, `sortBy` (`name`\|`size`) |
| `directory_tree` | Árbol recursivo en JSON | `path`, `excludePatterns` |
| `read_text_file` | Leer un archivo como texto UTF-8 | `path`, `head` o `tail` (n.º de líneas) |
| `read_media_file` | Leer un archivo binario y devolverlo en base64 con su MIME | `path` |
| `read_multiple_files` | Leer varios archivos en una sola llamada; un fallo no aborta el resto | `paths[]` |
| `search_files` | Búsqueda recursiva por patrón glob | `path`, `pattern`, `excludePatterns` |
| `get_file_info` | Metadatos: tamaño, fechas de creación/modificación/acceso, tipo, permisos | `path` |
| `write_file` | Crear o **sobrescribir** un archivo | `path`, `content` |
| `edit_file` | Ediciones selectivas por coincidencia de texto, con salida en formato diff y modo de prueba | `path`, `edits[] {oldText, newText}`, `dryRun` |
| `create_directory` | Crear directorio (y padres); es idempotente | `path` |
| `move_file` | Mover o renombrar; falla si el destino existe | `source`, `destination` |
| `list_allowed_directories` | Consultar el alcance vigente del servidor | — |

El servidor además marca cada herramienta con **anotaciones MCP** para que el cliente pueda
decidir qué requiere confirmación:

| Herramienta | `readOnlyHint` | `idempotentHint` | `destructiveHint` |
|---|---|---|---|
| Las 9 de lectura/listado | `true` | – | – |
| `create_directory` | `false` | `true` | `false` |
| `write_file` | `false` | `true` | `true` |
| `edit_file` | `false` | `false` | `true` |
| `move_file` | `false` | `false` | `true` |

Todas declaran `openWorldHint: false`: este servidor solo alcanza el sistema de archivos
local dentro de su alcance, nunca un mundo abierto o externo.

Detalle que conviene conocer: **no hay herramienta de borrado**. Eso no significa que no se
pueda destruir información — `write_file` sobrescribe sin preguntar y `move_file` mueve el
origen.

## 5.4 Cómo se delimita el alcance: *allowed directories*

Todas las operaciones están restringidas a una lista de **directorios permitidos**. Hay dos
formas de fijarla:

1. **Argumentos de línea de comandos**: las rutas que se pasan al arrancar el servidor
   (`mcp-server-filesystem /ruta1 /ruta2`).
2. **Roots del cliente** (método recomendado por el README del servidor): un cliente que
   soporte la primitiva *Roots* le comunica al servidor sus raíces —típicamente, la carpeta
   del workspace abierto— y esas raíces **reemplazan por completo** a los directorios
   configurados del lado del servidor. Permite actualizar el alcance en caliente, sin
   reiniciar el proceso, mediante `notifications/roots/list_changed`.

Reglas de borde:

- El servidor **exige al menos un directorio permitido** para operar. Si arranca sin
  argumentos y el cliente no soporta Roots (o entrega una lista vacía), falla en la
  inicialización.
- `list_allowed_directories` permite auditar en cualquier momento cuál es el alcance
  efectivo.

> Nota de versión (ver punto 4): *Roots* quedó **deprecada** en la revisión `2026-07-28`,
> con migración sugerida hacia parámetros de herramienta, URIs de recurso o configuración
> del servidor. El servidor de referencia todavía la usa, lo cual es esperable durante la
> ventana de deprecación.

## 5.5 Por qué existe ese límite y qué pasaría sin él

El límite existe porque **quien elige las rutas es un modelo, y el modelo decide a partir de
texto que puede no ser confiable** (ver punto 2). El directorio permitido es la traducción
del principio de mínimo privilegio a este contexto: convierte "acceso al disco" en "acceso
a esta carpeta".

Sin ese límite, un solo servidor de archivos conectado equivaldría a darle al asistente los
permisos completos del usuario del sistema operativo. Consecuencias concretas:

| Sin alcance limitado | Qué queda expuesto |
|---|---|
| Lectura arbitraria | `~/.ssh/id_rsa`, `~/.aws/credentials`, archivos `.env` con claves de API, cookies del navegador, historial, documentos personales. Todo eso además **se sube al contexto del modelo**, es decir, sale de la máquina |
| Escritura arbitraria | Sobrescribir `~/.bashrc`, `~/.zshrc`, un `LaunchAgent` de macOS, una tarea de `cron`, `~/.ssh/authorized_keys`, o el `package.json` de un proyecto. Escritura arbitraria equivale, en la práctica, a **ejecución de código** en el siguiente inicio de sesión |
| Movimiento/renombrado | Romper el sistema o un proyecto completo sin posibilidad de deshacer, porque no hay papelera |
| Combinación con inyección de instrucciones | Un archivo del propio proyecto con texto malicioso puede dirigir todas las operaciones anteriores. El usuario solo pidió "resume mis notas" |

Y un matiz importante: el alcance limitado es **una** capa, no la única. Es una restricción
implementada en JavaScript dentro del proceso del servidor, y por lo tanto puede tener
errores — de hecho los tuvo, con CVE asignados (ver punto 6). Un diseño razonable la
combina con: ejecutar el servidor con un usuario sin privilegios, montarlo en contenedor,
usar montajes de solo lectura cuando no se necesita escribir, y tener el directorio bajo
control de versiones para poder revertir.
